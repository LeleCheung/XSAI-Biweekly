# XSAI 双周报供稿工作流

本流程用于准备 XSAI 的常规双周报供稿。中文稿是事实来源；英文稿仅在中文确认后同步。所有调研、候选清单和草稿先保存在 `workplace/`，确认合入前不修改 `XiangShan-doc/`。

## 0. 确定边界

1. 记录本期双周报的截止时间、上一期已报道的 PR 和查询日期。
2. 以 PR 的 `mergedAt` 及目标分支为准，只考察已经合入的 PR；不能以 PR 编号、创建时间或 `closed` 状态代替。
3. 排除上一期已经报道的 PR。跨期漏项是否补报由负责人明确决定，不自行补入。

## 1. 收集候选 PR

1. 首先查询 XSAI、CUTE 和 difftest；只有改动与本组工作直接相关时，再查询 HBL2、XSAICache、xsai-env 或 NEMU。
2. 只保留已确认组员提交、且与 XSAI CPU、CUTE、缓存或验证基础设施直接相关的 PR。
3. 组员 GitHub 账号应维护在独立的确认名单中。当前已确认的映射为：
   - `Wonicon`：2017-王诲喆
   - `yu-yake2002`：2024-孙际儒
   - `ecall73`：2027-李智恒
4. 未合入、被拒绝、非组员或关联性不清楚的 PR 记录在审计清单中，不写入正式正文。

## 2. 核对事实与个人周报

1. 对每个候选 PR 阅读标题、描述、合入提交和必要的 diff，不只根据标题写作。
2. 在语雀中读取成员目录当级的个人文档；该文档本身可能持续记录各周进展，不能只查看其目录子节点。
3. 个人周报用于核对成果目标、影响和组内惯用表述；若个人周报未覆盖某项已合入 PR，仍以 PR 的事实为准。
4. 为每个候选记录作者、仓库、合入时间、证据、建议分类和排除理由，形成可追溯的候选清单。

## 3. 写中文 v1

1. 参照 Biweekly 101-108 的 `### XSAI` 结构，按实际内容选用一级分类，不保留空分类。
2. 已使用过的分类为：RTL 新特性、Bug 修复、代码质量、调试工具、评估工具、代码重构。
3. 每条使用“动作 + 对象 + 可理解的结果”的短句，并链接相应 PR。
4. 同一成果涉及多个仓库时合并为一个条目并附全部 PR；不要按仓库分段。
5. 同一个 PR 只归入一个最主要的一级分类。验证路径的错误应按实际影响判断为“Bug 修复”或“调试工具”，不要将其误写为硬件功能错误。
6. 性能数字、未确认的结论和开放 PR 不写入正文；待负责人确认的事项保留在审计清单。

## 4. 审阅中文 v1

1. 逐条确认 PR 已合入、作者已确认、链接正确、未在上一期报道。
2. 确认跨仓库改动没有重复报道，且分类反映读者可理解的主要成果。
3. 由 XSAI 负责人确认技术表述、性能数据和是否需要补漏后，中文稿才可进入翻译。

## 5. 同步英文稿

1. 先阅读 `XiangShan-doc/.github/agents/biweekly-translator.agent.md` 与 `.github/glossary.md`。
2. 保持中文、英文的标题层级、空行、列表层级、PR 链接、数字和代码标识符一致。
3. 已有术语按术语表使用；未收录的专有术语先从 PR 的英文标题和说明核对，仍不明确时请负责人确认。
4. 完成后核对中英文条目数、分类、PR 链接和技术事实一一对应。

## 6. 汇总分支协作

Biweekly 108 的 [汇总 PR #253](https://github.com/OpenXiangShan/XiangShan-doc/pull/253) 表明，常规协作方式是由总编辑创建汇总分支和 PR，各组负责人直接向该汇总分支提交各自的中英文段落。

1. 当前总编辑从 `master` 创建 `biweekly-{num}` 汇总分支，并向 `master` 创建汇总 PR。
2. XSAI 负责人在该分支上提交中英文 XSAI 段落，建议单独使用 `biweekly({num}): XSAI` 作为提交信息。Biweekly 108 的 XSAI 提交仅修改了对应的中文和英文双周报文件。
3. 推送到汇总分支需要对 `OpenXiangShan/XiangShan-doc` 的写权限。没有权限时，不向 `master` 直接提交；可请管理员授予权限，或从个人 fork 向汇总分支创建 PR，再由总编辑合入。
4. 总编辑负责汇总其他组提交、处理整体修改并合并最终 PR。

## 7. 合入正式仓库

1. 在总编辑创建汇总分支后、提交前，再次扫描自上次复查日至截稿时的新增已合入 PR。
2. 仅在中英文稿确认后，将 `### XSAI` 段落写入对应的 `XiangShan-doc/docs/blog/posts/biweekly-{num}.md` 与 `biweekly-{num}-en.md`。
3. 检查 Git diff 仅包含本组供稿的必要修改，再向汇总分支提交自己的 commit，交由双周报总编辑汇总。

## 固化方式

当前以本 Markdown 文档为准。它适合存放会变化的人员范围、仓库范围、审核口径和例外决定，也便于总编辑与组员共同审阅。连续两期按此流程稳定执行后，可将“查询已合入 PR、生成审计表、检查双语链接和结构”等机械步骤封装为 skills；skills 应引用本文件，而不替代负责人的技术判断和最终确认。
